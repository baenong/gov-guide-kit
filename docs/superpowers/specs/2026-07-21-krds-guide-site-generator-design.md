# 공공기관 민원 안내 사이트 생성기 설계

- 작성일: 2026-07-21
- 범위: 두 개의 하위 시스템 중 **1단계 — 사이트 생성기/배포 파이프라인**만 다룸. 2단계(비개발자용 GUI 콘텐츠 에디터)는 별도 스펙으로 분리.

## 배경 및 목적

공공기관이 민원인·신청인 대상 안내 페이지(공지, 절차, 서류, 서식, Q&A 등)를 손쉽게 만들고 배포할 수 있는 **재사용 가능한 범용 도구**. 특정 기관 1회성 사이트가 아니라, GitHub 템플릿 저장소를 fork/clone해서 여러 기관이 각자의 안내 사이트를 만드는 데 반복 사용하는 것을 전제로 한다. 로그인, API, 데이터베이스 등 백엔드 기능은 구현하지 않으며 순수 정적 사이트로 동작한다. 콘텐츠 작성자는 비개발자(공무원)이므로, 원시 마크다운 문법을 최대한 단순화하고 실수를 빌드 타임에 잡아내는 것이 핵심 설계 목표다.

## 기술 스택

- **Astro** — 정적 사이트 생성기. 상호작용이 필요한 부분(캘린더)만 클라이언트 JS로 실행되는 island 구조를 채택해, 나머지 페이지는 순수 HTML/CSS로 출력된다.
- **Astro Content Collections + Zod** — front matter 스키마를 코드로 정의하고 빌드 타임에 검증. 비개발자가 흔히 저지르는 형식 오류(숫자 필드에 문자열 입력 등)를 사람이 읽을 수 있는 에러 메시지로 막는다.
- **remark-directive** — `:::타입 ... :::` 컨테이너 문법으로 강조 섹션·캘린더 같은 커스텀 블록을 순수 마크다운 확장으로 구현. MDX/JSX 컴포넌트 태그는 사용하지 않는다(비개발자가 다룰 문법을 최소화하기 위함).
- **커스텀 remark 플러그인** — 첨부파일(비이미지 링크)을 감지해 파일 카드 UI로 자동 변환.
- Node/npm 빌드 스텝은 있으나, 콘텐츠 저작자는 이를 직접 실행할 필요가 없다(배포 파이프라인이 자동 처리).

## 정보구조 및 콘텐츠 모델

- 저장소 구조: `src/content/guide/*.md` — 파일 하나가 페이지 하나. `index.md`가 메인 페이지(공지 + 캘린더 포함, `order: 0` 고정).
- Front matter 스키마 (Zod):
  ```ts
  title: string;       // 필수, 페이지 제목이자 사이트 내비게이션 라벨
  order: number;       // 필수, 좌측 내비게이션 정렬 순서
  description?: string; // 선택, meta description
  ```
- 좌측 사이트 내비게이션은 모든 콘텐츠 파일의 `order`를 읽어 빌드 시 자동 생성된다. 별도 nav 설정 파일은 두지 않는다 — 저작자는 md 파일의 front matter만 관리하면 된다.
- 페이지 내 목차(TOC)는 본문의 H2/H3 헤딩을 빌드 타임에 파싱해 자동 생성하며, 좌측 사이트 내비게이션과는 별개 기능이다.
- 페이지 간 링크는 표준 마크다운 상대경로 링크를 사용하고 Astro 라우팅이 그대로 해석한다.
- 순서 있는/없는 리스트는 표준 마크다운 문법을 그대로 사용하고 KRDS 스타일만 CSS로 입힌다.

## 커스텀 마크다운 블록

- **강조 섹션**: `:::notice`, `:::warning` 등 컨테이너 문법. 일반 마크다운 뷰어에서는 텍스트로만 보여 깨지지 않는다.
- **캘린더**: `:::calendar` 블록 안에 저작자가 `- YYYY-MM-DD: 제목` 형식의 리스트를 직접 나열한다. 빌드 시 이를 파싱해 월별 그리드 컴포넌트로 렌더링하고, 월 이동 등 상호작용은 클라이언트 JS(Astro island)로 처리한다.
- **첨부파일**: 별도 문법 없이 표준 마크다운 링크(`[파일명](assets/files/xxx.pdf)`)를 사용한다. 빌드 시 remark 플러그인이 링크 대상이 이미지가 아닌 파일임을 감지해 확장자 아이콘 + 파일명 + 다운로드 버튼을 가진 카드 UI로 자동 변환한다.
- **이미지**: 표준 `![alt](경로)` 문법. 반응형(최대 너비 제한)과 lazy loading을 빌드 시 자동 적용한다.

## 브랜딩 / 기관별 설정

- 저장소 루트의 `site.config.ts` 파일 하나에 기관별 설정을 집중한다:
  ```ts
  export default {
    orgName: string,
    colors: { primary: string, secondary: string, accent: string },
    logoPath: string,
  }
  ```
- 색상 값은 빌드 시 CSS 커스텀 프로퍼티(`--color-primary` 등)로 변환되어 전역 적용되며, 모든 KRDS 컴포넌트는 이 변수만 참조한다.
- 새 기관이 템플릿을 재사용할 때는 `site.config.ts`, 로고 파일, `src/content/guide/*.md` 콘텐츠만 교체하면 된다 — 컴포넌트/레이아웃 코드는 건드리지 않는다.
- 빌드 스크립트가 `primary`/`secondary` 색상 조합에 대해 WCAG 2.1 AA 명도 대비 기준(본문 4.5:1 이상)을 자동 체크하고, 기준 미달 시 빌드 경고를 출력한다.

## KRDS 디자인 시스템 적용

- 타이포그래피: Pretendard, 본문 16px/line-height 1.6, 최소 본문 크기 14px 미만 금지, KRDS 헤딩 스케일 준수.
- 레이아웃: 좌측 사이트 내비게이션 + 우측 본문의 반응형 구성. 모바일에서는 햄버거 오프캔버스 드로어(배경 딤, ESC/바깥 클릭/닫기 버튼으로 닫힘, 포커스 트랩)로 전환.
- 접근성: 키보드 내비게이션, 스크린리더 라벨, 명확한 포커스 표시, 명도 대비 기준 준수. 로그인/검색 등 불필요한 기능은 배제해 인터페이스를 단순화한다.

## 배포

- **Vercel 우선**: 저장소를 Vercel에 연결하면 `git push` 시 자동 빌드/배포. Astro 기본 정적 출력과 별도 설정 없이 호환된다.
- **GitHub Pages 겸용**: `astro.config.ts`의 `site`/`base` 값을 배포 대상에 따라 환경변수로 분기하고, `.github/workflows/deploy.yml` GitHub Actions로 `main` push 시 GitHub Pages에도 배포할 수 있게 한다. Vercel 계정이 없는 기관도 GitHub Pages만으로 무료 운영이 가능하다.
- 두 배포 경로 모두 콘텐츠 저작자가 직접 개입할 필요가 없다 — 콘텐츠를 push하기만 하면 배포까지 자동 완료된다.

## 검증

- 빌드 타임: Zod 스키마 검증(front matter 형식 오류 검출), 색상 대비 자동 체크.
- 링크/이미지 경로 검사(html-proofer 또는 Astro 내장 체크)로 깨진 내부 링크나 잘못된 첨부파일 경로를 빌드 단계에서 검출.
- 로컬 미리보기(`npm run dev`)는 개발자용이며, 비개발자 저작자는 이 단계를 건너뛰고 push 후 Vercel 프리뷰 URL로 결과를 확인한다.

## 범위 밖 (Out of Scope)

- 비개발자용 GUI 콘텐츠 에디터(슬래시 명령/우클릭 메뉴로 마크다운 자동 삽입) — 별도 프로젝트/스펙으로 진행.
- 로그인, 검색, 다국어, 커스텀 도메인, 백엔드/API/데이터베이스 기능 일체.
- 특정 기관(예: 군산시)의 실제 콘텐츠 내용 — 이 스펙은 재사용 가능한 생성기 자체만 다루며, 실 콘텐츠는 이 템플릿을 fork한 개별 사이트 저장소에서 채워진다.
